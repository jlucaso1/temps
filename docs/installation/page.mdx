## Database Setup

Temps requires **PostgreSQL with TimescaleDB**. Choose one of these options:

### Option 1: Docker (Recommended)

The easiest way to run PostgreSQL with TimescaleDB:

```bash
# Create a persistent volume
docker volume create temps-postgres

# Start TimescaleDB on port 16432 (avoids conflicts with existing PostgreSQL)
docker run -d \
  --name temps-postgres \
  --restart unless-stopped \
  -v temps-postgres:/home/postgres/pgdata/data \
  -e POSTGRES_USER=postgres \
  -e POSTGRES_PASSWORD=temps \
  -e POSTGRES_DB=temps \
  -p 16432:5432 \
  timescale/timescaledb-ha:pg18

# Verify it's running
docker ps | grep temps-postgres
```

### Option 2: Native Installation

If you need native PostgreSQL, you must install TimescaleDB separately:

<CodeGroup>

```bash {{ title: 'Ubuntu/Debian' }}
# Add PostgreSQL repository
sudo sh -c 'echo "deb http://apt.postgresql.org/pub/repos/apt $(lsb_release -cs)-pgdg main" > /etc/apt/sources.list.d/pgdg.list'
wget --quiet -O - https://www.postgresql.org/media/keys/ACCC4CF8.asc | sudo apt-key add -

# Add TimescaleDB repository
sudo sh -c "echo 'deb https://packagecloud.io/timescale/timescaledb/ubuntu/ $(lsb_release -c -s) main' > /etc/apt/sources.list.d/timescaledb.list"
wget --quiet -O - https://packagecloud.io/timescale/timescaledb/gpgkey | sudo apt-key add -

# Install PostgreSQL and TimescaleDB
sudo apt-get update
sudo apt-get install -y postgresql-15 timescaledb-postgresql-15

# Configure TimescaleDB
sudo timescaledb-tune --quiet --yes
sudo systemctl restart postgresql

# Create database and enable extension
sudo -u postgres createdb temps
sudo -u postgres psql temps -c "CREATE EXTENSION IF NOT EXISTS timescaledb;"
```

```bash {{ title: 'macOS (Homebrew)' }}
# Install PostgreSQL and TimescaleDB
brew install postgresql@15
brew install timescaledb

# Configure TimescaleDB
timescaledb-tune --quiet --yes

# Restart PostgreSQL
brew services restart postgresql@15

# Create database and enable extension
createdb temps
psql temps -c "CREATE EXTENSION IF NOT EXISTS timescaledb;"
```

</CodeGroup>

## Installing Temps

### Quick Install (Recommended)

Install Temps with a single command:

```bash
curl -fsSL https://temps.sh/deploy.sh | bash
```

The installer will:

- Detect your platform (Linux/macOS, AMD64/ARM64)
- Download the appropriate binary
- Install to `~/.temps/bin/`
- Add to your PATH

After installation, restart your shell or run:

```bash
source ~/.zshrc  # or ~/.bashrc
temps --version
```

### Homebrew (macOS)

```bash
# Add the Temps tap
brew tap gotempsh/tap

# Install Temps
brew install temps

# Verify installation
temps --version

# Upgrade to latest version
brew upgrade temps
```

### Build from Source

Install the local build prerequisites before compiling from source. The release build compiles native Rust dependencies, OpenTelemetry protobufs, and the web UI bundle.

```bash {{ title: 'Amazon Linux 2023 prerequisites' }}
sudo dnf groupinstall -y "Development Tools"
sudo dnf install -y \
  rust cargo rustfmt rust-std-static-wasm32-unknown-unknown \
  cmake pkgconf-pkg-config openssl-devel protobuf-compiler \
  perl-FindBin perl-IPC-Cmd perl-File-Compare perl-File-Copy perl-Time-Piece

cargo install wasm-pack
```

For Debian/Ubuntu, macOS, and contributor setup details, see [CONTRIBUTING.md](https://github.com/gotempsh/temps/blob/main/CONTRIBUTING.md#prerequisites).

```bash
# Clone the repository
git clone https://github.com/gotempsh/temps.git
cd temps

# Build release binary (includes web UI)
cargo build --release

# Install
sudo cp target/release/temps /usr/local/bin/
temps --version
```

### Docker Compose from Source

The repository Compose stack requires independent URL-safe database and Redis
passwords. Copy the template and generate 256-bit hexadecimal values (do not
use URI punctuation, because the values are also used in connection URLs):

```bash
install -m 600 .env.example .env
openssl rand -hex 32  # set as POSTGRES_PASSWORD
openssl rand -hex 32  # set as REDIS_PASSWORD
# Set TEMPS_ADMIN_EMAIL to the initial administrator's email address.
# Create its password as a permission-restricted Compose secret:
mkdir -p secrets
chmod 700 secrets
{ printf 'tT3!'; openssl rand -hex 32; } > secrets/admin_password
chmod 444 secrets/admin_password
# Set DOCKER_GID to the container-visible socket group on Linux or macOS:
# docker run --rm -v /var/run/docker.sock:/var/run/docker.sock alpine:3.22 stat -c '%g' /var/run/docker.sock
docker compose up --build --detach
```

The Docker builder compiles Temps inside Alpine, so the resulting binary
matches the host architecture and the musl-based runtime even when Compose is
invoked from macOS or a glibc Linux distribution.

Keep `.env` owned by the account that operates Temps and mode `0600`; it
contains credentials that can access the loopback-published data services.

Compose validates the password alphabet before starting data services. It
publishes PostgreSQL, Redis, and the console API on loopback only; HTTP and
HTTPS remain publicly bound. Temps receives Docker-socket access through the
socket owner's group while the application process remains non-root. Treat
membership in that group as root-equivalent host access.
On the first unattended startup, Temps creates `TEMPS_ADMIN_EMAIL` as the
administrator using the mounted `TEMPS_ADMIN_PASSWORD_FILE`. The password is
not placed in the container environment, command line, or logs. The source file
must be `0444` so the image's non-root UID can read—but not modify—the bind-mounted secret on
Linux; its `0700` parent directory prevents other host users from traversing to
it. Rotate the password after first login.

## Running Temps

### Basic Usage

```bash
temps serve \
  --address 0.0.0.0:8080 \
  --database-url postgresql://postgres:temps@localhost:16432/temps
```

### Using Environment Variables

```bash
export TEMPS_ADDRESS=0.0.0.0:8080
export TEMPS_DATABASE_URL=postgresql://postgres:temps@localhost:16432/temps

temps serve
```

### Configuration Options

| Environment Variable    | CLI Flag            | Default          | Description                                 |
| ----------------------- | ------------------- | ---------------- | ------------------------------------------- |
| `TEMPS_ADDRESS`         | `--address`         | `127.0.0.1:3000` | HTTP server address                         |
| `TEMPS_DATABASE_URL`    | `--database-url`    | (required)       | PostgreSQL connection string                |
| `TEMPS_TLS_ADDRESS`     | `--tls-address`     | (optional)       | HTTPS server address                        |
| `TEMPS_DATA_DIR`        | `--data-dir`        | `~/.temps`       | Data directory for keys/config              |
| `TEMPS_LOG_LEVEL`       | `--log-level`       | `info`           | Log level (trace, debug, info, warn, error) |
| `TEMPS_CONSOLE_ADDRESS` | `--console-address` | (optional)       | Admin console address                       |

## First Run

On first run, Temps automatically:

1. Creates data directory at `~/.temps`
2. Generates encryption keys and auth secrets
3. Runs all database migrations
4. Creates the default admin user

**Save your credentials!** The first login credentials are displayed in the console output.

## Production Deployment

### Systemd Service

Create a systemd service for production:

```bash
sudo tee /etc/systemd/system/temps.service > /dev/null <<EOF
[Unit]
Description=Temps Platform
After=network.target postgresql.service

[Service]
Type=simple
User=temps
WorkingDirectory=/opt/temps
Environment="TEMPS_DATABASE_URL=postgresql://temps:password@localhost/temps"
Environment="TEMPS_ADDRESS=0.0.0.0:8080"
Environment="TEMPS_TLS_ADDRESS=0.0.0.0:8443"
ExecStart=/usr/local/bin/temps serve
Restart=always
RestartSec=10

[Install]
WantedBy=multi-user.target
EOF

# Enable and start
sudo systemctl daemon-reload
sudo systemctl enable temps
sudo systemctl start temps

# Check status
sudo systemctl status temps
```

### Memory Footprint and Transparent Huge Pages

The `temps` binary uses [jemalloc](https://jemalloc.net/) as its global
allocator. jemalloc keeps up to `4 x CPU cores` independent arenas so that
allocating threads rarely contend on the same one, and binds threads to them
lazily as they first allocate. Every arena that is used maps its own region from
the kernel, and the kernel returns huge-page-aligned mappings when Transparent
Huge Pages (THP) are enabled.

When the host is set to `THP=always` -- the default on many distributions --
touching a single byte inside such a window can fault in the whole huge page.
An arena holding a few kilobytes of metadata is then charged the full huge page.
The cost scales with the number of arenas actually used, not with how much
memory Temps allocates, so it is most visible on many-core machines running a
light workload.

The figures below were measured on x86_64 with 4 KiB base pages, where a huge
page is 2 MiB. On ARM64 the page geometry depends on the kernel's base page size
(4 KiB, 16 KiB or 64 KiB), and the huge page can be considerably larger, so the
absolute numbers do not carry over.

Check the current setting:

```bash
cat /sys/kernel/mm/transparent_hugepage/enabled
# [always] madvise never   <- inflated RSS
# always [madvise] never   <- nothing to do
```

Switching the host to `madvise` leaves THP available to processes that ask for
it explicitly and stops the kernel from handing whole huge pages to processes
that do not:

```bash
# Takes effect immediately, for every process started afterwards
echo madvise | sudo tee /sys/kernel/mm/transparent_hugepage/enabled
```

To persist it across reboots, add `transparent_hugepage=madvise` to the kernel
command line. The command differs by distribution:

```bash
# Debian / Ubuntu -- edit GRUB_CMDLINE_LINUX in /etc/default/grub, then:
sudo update-grub

# RHEL / Amazon Linux -- no file to edit:
sudo grubby --update-kernel=ALL --args="transparent_hugepage=madvise"

# Other GRUB 2 systems -- edit GRUB_CMDLINE_LINUX in /etc/default/grub, then:
sudo grub2-mkconfig -o /boot/grub2/grub.cfg
```

Restart Temps after changing the runtime setting -- it is applied when memory is
mapped, so an already-running process keeps the huge pages it was given.

**Measured effect.** On a 24-core x86_64 host, after an identical warmup, with
swap disabled for the service (`MemorySwapMax=0`) so that resident memory cannot
be hidden in swap:

| Host setting  | VmRSS  | RssAnon | Huge-page backed |
| ------------- | ------ | ------- | ---------------- |
| `THP=always`  | 442 MB | 332 MB  | 190 MB           |
| `THP=madvise` | 319 MB | 210 MB  | 0 MB             |

Switching to `madvise` cut the resident set by 123 MB, about 28%. On that host
190 MB of the 442 MB -- roughly 43% -- was huge pages backing sparsely used
allocator regions. A 2-core VPS sees a much smaller absolute difference, because
it uses at most a twelfth as many arenas.

**Trade-off.** This is a host-wide kernel setting, not a Temps setting, so it
applies to every process on the machine. It does not affect *explicit* huge
pages: hugetlbfs reservations, including PostgreSQL's `huge_pages` setting, are
a separate mechanism and keep working under `madvise`. PostgreSQL in fact
[discourages THP](https://www.postgresql.org/docs/current/runtime-config-resource.html#RUNTIME-CONFIG-RESOURCE-MEMORY)
and asks for huge pages explicitly instead. What you should check before
flipping the host is whether some other workload on it relies on THP being
granted without asking -- a JVM run with `-XX:+UseTransparentHugePages`, for
example. If nothing on the host does, `madvise` is the safer default.

**Verifying on your own host.** Reading another process's memory summary goes
through the kernel's ptrace access checks, so unless you are running as the same
user as the service, use `sudo`:

```bash
sudo grep -E 'VmRSS|RssAnon|VmSwap' /proc/$(pidof temps)/status
sudo grep AnonHugePages /proc/$(pidof temps)/smaps_rollup
```

Report `RssAnon` and `VmSwap` together: on a host with swap enabled, a falling
RSS may only mean pages moved into swap.

Two adjustments that look like they should replace the host setting do not:

- jemalloc's `thp:never` does issue `MADV_NOHUGEPAGE`, but not over every
  mapping the allocator ends up using, so a large share of the huge pages
  survives it. Its net effect is host-dependent: in one controlled reproduction
  it roughly halved the huge-page-backed memory, while on the 24-core host above
  it did not reduce it at all and total RSS rose. It is not a substitute for the
  host setting.
- Shrinking thread stacks with `RUST_MIN_STACK` does not touch this memory at
  all: glibc already marks every thread stack `MADV_NOHUGEPAGE`, so stacks are
  never huge-page backed. It only shifts the address-space layout, and has been
  measured to raise resident memory substantially.

### Reverse Proxy (nginx)

If you're running behind nginx:

```nginx
server {
    listen 80;
    server_name temps.yourdomain.com;

    location / {
        proxy_pass http://localhost:8080;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection 'upgrade';
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_cache_bypass $http_upgrade;
    }
}
```

## Data Directory

Temps stores sensitive data in `~/.temps` by default:

```
~/.temps/
├── encryption_key    # AES-256 encryption key (auto-generated)
└── auth_secret       # Session authentication secret (auto-generated)
```

These files are **automatically backed up** by Temps when you configure S3 backup storage. You can also manually back them up for extra safety.

## Troubleshooting

### Database Connection Error

```bash
# If using Docker
docker ps | grep temps-postgres  # Ensure container is running
docker logs temps-postgres       # Check for errors

# Test connection
psql postgresql://postgres:temps@localhost:16432/temps
```

### TimescaleDB Extension Not Found

This error means TimescaleDB is not installed:

```
extension "timescaledb" is not available
```

**Solution:** Use the Docker method (easiest) or install the TimescaleDB package for your PostgreSQL version.

### Port Already in Use

```bash
# Find process using port
lsof -i :8080

# Use different port
temps serve --address 0.0.0.0:9000
```

### Permission Denied

```bash
# Check data directory permissions
ls -la ~/.temps/

# Fix permissions
chmod 700 ~/.temps/
chmod 600 ~/.temps/encryption_key
chmod 600 ~/.temps/auth_secret
```
